원인을 분석하기 위해 Gemini와 Codex(두 개의 AI)에게 심층 분석을 의뢰했습니다.

두 AI가 찾은 공통 원인

원인 1: 리뷰가 "충분히 좋아서" 질문이 안 생긴다

수강생은 이미 "리뷰 수신 → 읽음 → 수정 → PR 업데이트 → 새 리뷰 수신" 루프에 만족하고 있었습니다.
추가 질문이나 반박의 니즈 자체가 없었습니다.

원인 2: @sparta 멘션을 발견하려면 5단계를 거쳐야 한다 
리뷰 읽음 → 하단 CTA "질문하기" 클릭 → 릴리즈 노트 페이지 로딩
→ "@sparta 멘션 사용법" 확인 → 다시 GitHub PR로 돌아감 → 댓글에 @sparta 입력

최소 5단계의 능동적 행동이 필요했습니다.
핵심 통찰: "부가 기능"이라는 개념 자체가 문제

사용자는 "핵심 기능"과 "부가 기능"을 구분하지 않습니다.
하나의 리뷰 흐름이 있을 뿐입니다.
부가 기능이 사용되려면 별개의 기능이 아니라 리뷰 경험의 자연스러운 연속이어야 합니다.

## 🤔 생각해보기

효과: 질문을 읽는 순간 자연스럽게 머릿속에서 답을 생각하게 됨 (실제 학습)

멘토와 시니컬, 다른 질문을 던집니다

두 페르소나가 각각의 톤에 맞는 질문을 자동 생성합니다.

페르소나질문 톤예시
멘토
10년차 시니어		 학습적
원리와 트레이드오프를 고민하게 만드는 열린 질문		 "이 패턴을 대규모 트래픽 환경에서도 동일하게 적용할 수 있을까요?"
시니컬
15년차 원칙주의자		 도전적
운영 환경에서 어떻게 실패할 수 있는지를 생각하게 만드는 질문		 "이 예외 처리 방식은 외부 API 응답이 10초 지연되면 어떤 연쇄 장애를 유발할까요?"

어떻게 구현했나요?

새로운 API 호출 없이, 프롬프트에 질문 생성 지시를 추가하는 것으로 구현했습니다.

1차
프롬프트에 "생각해보기" 섹션 추가

AI가 이미 리뷰한 코드의 맥락을 알고 있으므로, 템플릿에 섹션만 추가하면
별도 API 호출 없이 컨텍스트에 맞는 질문이 자동 생성됩니다.

2차
shields.io 뱃지 → 텍스트 인라인 교체

외부 CDN 의존(shields.io)을 제거하고, 프롬프트 내에 @sparta 멘션 예시를
자연스럽게 포함시켰습니다. 추가 비용 없이 전환했습니다.

3차
중복 방지 로직

AI가 프롬프트를 충실히 따르면 @sparta 유도가 이미 포함되어 있습니다.
이 경우 하단 보조 유도는 자동으로 생략됩니다.

if (content.contains("@sparta")) {
    // 프롬프트에서 이미 유도 → 하단 CTA 생략
    return content;
}
// AI가 누락한 경우에만 보조 유도 삽입
