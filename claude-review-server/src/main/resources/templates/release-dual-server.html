홈서버 + 개발PC 이중화

왜 이중화가 필요한가?

홈서버는 24시간 운영되지만, 전원 문제, 네트워크 장애, Docker 크래시 등으로 서비스가 중단될 수 있습니다. 수강생 7개 팀이 AI 리뷰에 의존하는 상황에서 장애 시간은 곧 과제 지연으로 이어집니다.

이제 개발PC가 대기 서버(Standby)로 동작하여, 홈서버 장애 시 자동으로 서비스를 인계합니다. 수강생은 장애를 인지하지 못합니다.

아키텍처

                Cloudflare Edge
            review.example.com
                        │
            DNS CNAME (TTL=1, 프록시=즉시 전파)
                        │
        ┌───────────────┼───────────────┐
        │ 정상: Tunnel A│ 장애: Tunnel B│
        ▼               │               ▼
  ┌───────────┐        │        ┌───────────┐
  │  홈서버   │        │        │  개발PC    │
  │  ACTIVE   │        │        │  STANDBY   │
  │  :8080    │        │        │  :18080   │
  │  Tunnel A │        │        │  Tunnel B │
  └───────────┘        │        └───────────┘
        ▲               │               │
        │   rsync (5분 간격)             │
        └────────────────────────────────┘

  GitHub Actions Watchdog: 5분 간격 이중 헬스체크
    Active 서버: https://review.example.com/health
    Primary 직접: https://primary.example.com/health (항상 Tunnel A)

  페일오버: Active 3회 실패 → 즉시 Standby 전환
  자동복구: Primary 안정성 검증(2/2 성공) 후 → Primary 복원
  수동 전환: GitHub UI → Actions → Failover Watchdog → Run workflow
1

시나리오 1: 평소 (모든 것이 정상)

수강생은 아무것도 모릅니다
수강생이 PR을 열면 AI 리뷰가 달립니다

평소와 완전히 동일합니다. 수강생은 뒤에서 두 대의 서버가 돌고 있는지 모릅니다.

수강생: PR 오픈
  → GitHub Actions → POST /review
  → Cloudflare → Tunnel A → 홈서버
  → AI 리뷰 코멘트 달림 (10~30초)
5분마다 와치독이 조용히 돕니다

GitHub Actions가 이중 헬스체크를 수행합니다. 모두 정상이면 아무 일도 일어나지 않습니다. 이게 정상입니다.

[12:00] Active 체크: 200 OK / Primary 체크: 200 OK → 정상. 아무것도 안 함.
[12:05] Active 체크: 200 OK / Primary 체크: 200 OK → 정상. 아무것도 안 함.
[12:10] Active 체크: 200 OK / Primary 체크: 200 OK → 정상. 아무것도 안 함.
2

시나리오 2: 홈서버 장애 → 자동 페일오버

수강생 체감 장애: 최대 ~5분
12:12 — 홈서버가 죽었습니다

전원 차단, 네트워크 단절, Docker 크래시 등 원인은 상관없습니다. 이때 수강생이 PR을 열면 리뷰 응답이 없습니다(timeout).

12:15 — 와치독이 장애를 감지합니다

5분 주기 와치독이 Active 서버 헬스체크 3회 연속 실패를 확인합니다.

Active 헬스체크: 000 FAIL (1/3) → 5초 대기
Active 헬스체크: 000 FAIL (2/3) → 5초 대기
Active 헬스체크: 000 FAIL (3/3) → 임계값 도달! 페일오버 트리거!
12:15 — DNS를 즉시 전환합니다

Cloudflare API로 CNAME을 Tunnel B(개발PC)로 변경. TTL=1 + 프록시 = 즉시 전파. 10초 후 새 대상 서버 헬스체크까지 검증합니다.

DNS: review.example.com → Tunnel A 에서 Tunnel B 로 변경
검증: https://review.example.com/health → 200 OK
12:16 — 수강생의 다음 PR은 정상 처리됩니다

트래픽이 개발PC로 라우팅되어 서비스가 계속됩니다. 수강생은 "아까 잠깐 느렸네?" 정도로만 인식합니다.

3

시나리오 3: Standby로 운영 중

수강생은 평소와 동일하게 이용
개발PC가 트래픽을 받습니다

페일오버 이후 모든 리뷰 요청이 개발PC(:18080)에서 처리됩니다. 수강생 관점에서는 완전히 정상 동작입니다.

와치독은 계속 Primary를 감시합니다

DNS가 Standby를 가리키고 있어도, 전용 엔드포인트로 홈서버 복구를 계속 확인합니다.

[12:20] Active(개발PC): 200 OK / Primary 직접체크: 000 FAIL → Standby 유지
[12:25] Active(개발PC): 200 OK / Primary 직접체크: 000 FAIL → Standby 유지
[12:30] Active(개발PC): 200 OK / Primary 직접체크: 000 FAIL → Standby 유지
4

시나리오 4: 홈서버 복구 → 자동 원복

관리자 개입 없이 자동 복구
홈서버가 복구됩니다

전원 복구 후 Docker Compose의 restart: unless-stopped 정책으로 컨테이너가 자동 시작됩니다.

전용 엔드포인트로 복구를 감지합니다

와치독이 primary.example.com으로 홈서버를 직접 체크합니다. 200 OK가 오면 안정성 검증을 시작합니다.

[14:05] Primary 직접체크: 200 OK → "Primary가 살아났다. 안정성 검증 시작"
        안정성 검증 1/2: 15초 대기 → 200 OK
        안정성 검증 2/2: 15초 대기 → 200 OK
        → 2/2 성공! 자동 복구 실행!

        DNS: review.example.com → Tunnel B 에서 Tunnel A 로 복원
        검증: 200 OK → 자동 복구 완료
수강생은 인지하지 못합니다

트래픽이 다시 홈서버로 라우팅되고, 개발PC는 Standby 대기 상태로 돌아갑니다. 처음부터 끝까지 관리자 개입이 없습니다.

5

시나리오 5: Flapping 방지

불안정한 복구는 자동으로 차단
홈서버가 살아났다가 다시 죽는 경우

안정성 검증 2회 중 1회라도 실패하면 복구를 취소하고 다음 5분 주기를 기다립니다.

[14:05] Primary 직접체크: 200 OK → 안정성 검증 시작
        안정성 검증 1/2: 200 OK
        안정성 검증 2/2: 000 FAIL → 불안정! 복구 취소.
        → 다음 5분 주기에서 재시도.

[14:10] Primary 직접체크: 000 FAIL → 여전히 불안정. 대기.
6

시나리오 6: 수동 전환

관리자가 의도적으로 서버 전환
홈서버 배포 작업 등으로 의도적 전환이 필요한 경우

GitHub UI에서 버튼 클릭으로 즉시 전환합니다.

GitHub UI → Actions 탭 → Failover Watchdog → Run workflow
  → Action: switch-standby 선택 → Run
  → 즉시 개발PC로 전환. 홈서버는 배포 작업 가능.

배포 완료 후:
  → Action: switch-primary 선택 → Run
  → 즉시 홈서버로 복원.

상태 전이 요약

                    페일오버 (Active 3회 실패)
     PRIMARY ──────────────────────────────────→ STANDBY
     (홈서버)                                    (개발PC)
       ▲                                           │
       │          자동 복구                         │
       └── Primary 안정성 검증 2/2 성공 ───────────┘

     수동 전환: GitHub Actions → switch-primary / switch-standby
     Flapping 방지: 안정성 검증 실패 시 다음 주기로 연기

기술 스펙

전환 방식Cloudflare DNS API — CNAME 레코드 전환 (TTL=1, 즉시 전파)
페일오버 감지GitHub Actions 와치독 5분 간격, 이중 헬스체크 (Active + Primary 직접)
자동 복구Primary 직접 체크 + 안정성 검증(2/2) 후 자동 복원, Flapping 방지
모니터링 엔드포인트primary.example.com (항상 Tunnel A, Primary 직접 체크용)
RTO최대 약 5분 (와치독 주기 + 헬스체크 + DNS 전환)
Standby 포트18080 (개발PC 로컬 개발 8080과 분리)
리소스 제한CPU 0.5코어, 메모리 512MB — 개발 작업 영향 최소화
데이터 동기화rsync (5분 간격, 설정/로그)
비용0원 (Cloudflare Free + DNS API 무료)
헬스체크/health 응답에 role 필드 추가 (active/standby 구분)
